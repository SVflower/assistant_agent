## 1. 产品愿景

建设一个可嵌入企业业务系统、可连接客户数据和知识资产、能够完成工业问答与确定性分析的
**工业智能 Agent 平台**。

平台不只是把大模型接入 MES，也不把模型包装成新的报表入口。它需要把自然语言问题转化为
受控的业务查询、知识检索和分析任务，向用户交付带口径、时间、来源、质量说明和可视化的结果。

一句话定位：

> 让现场、工艺、质量、设备和管理人员用业务语言获取可信工业事实，并在统一安全边界内调用
> 企业知识、业务系统和确定性分析能力。

长期产品价值来自四项组合能力：

1. **Agent 编排内核**：理解问题，规划并协调知识、数据和分析能力。
2. **工业语义与契约**：统一指标、维度、时间、来源、质量和分析结果表达。
3. **开放扩展生态**：Skill、Knowledge Provider、MCP、Analysis Provider 均可外部接入。
4. **企业治理边界**：权限、隔离、审计、预算、恢复、版本和数据安全由平台统一控制。

## 2. 目标客户与核心用户

### 2.1 目标客户

- 已部署 MES、WMS、QMS、ERP、Historian 或设备数据平台，但系统间信息割裂的制造企业；
- 数据已经积累，但依赖 IT 或数据团队临时取数的企业；
- 希望复用现有知识库、算法平台和业务接口，而不是被迫迁移到单一 AI 平台的企业；
- 对私有部署、数据不出域、结果可追溯和操作可审计有明确要求的企业；
- 光伏、锂电、半导体、电子制造、机械加工等质量和工艺数据密集行业。

### 2.2 核心用户

| 用户 | 高频问题 | 主要价值 |
|---|---|---|
| 生产管理 | 今日产量、计划达成、瓶颈、停机损失 | 减少跨系统汇总和等待报表 |
| 工艺工程师 | 参数漂移、效率分布、Recipe 对比、异常批次 | 快速形成可复核的分析路径 |
| 质量工程师 | 良率、缺陷 Pareto、SPC、过程能力、追溯 | 统一统计口径并保留证据 |
| 设备工程师 | 报警、故障、MTBF/MTTR、设备对标 | 联合实时数据、手册和历史案例 |
| 仓储与物流 | 箱盒查询、库存、批次流向、影响范围 | 通过业务语言完成跨层级追溯 |
| 管理人员 | 关键指标、异常影响、行动进展 | 获取有时间和范围说明的结论 |
| IT/数据团队 | 接口治理、权限、审计、算法复用 | 避免每个问答场景重复建设 |

## 3. 客户痛点

### 3.1 系统很多，但问题仍需要人工拼接

MES 提供生产事实，QMS 提供质量结果，WMS 提供物料流向，Historian 保存设备时序，文档平台保存
SOP 和设备手册。一个实际问题往往需要跨多个系统查询，再由工程师用 Excel 或脚本拼接。

传统报表只能回答预定义问题；临时问题仍要提工单、找 IT、导数据和人工核对。

### 3.2 指标同名但口径不同

“今日产量”“良率”“效率”“停机时间”可能因生产日、班次、工序、返工规则和数据截至时间不同而
得出不同结果。普通自然语言问答如果没有指标语义层，很容易给出看似正确但口径错误的答案。

### 3.3 工业数据量远超模型上下文

百万级电池片检测记录、秒级设备时序和长期生产明细不适合直接传给大模型。直接传输会造成成本、
延迟、上下文溢出、计算错误和数据泄露风险。

### 3.4 知识存在，但难以在现场问题中使用

SOP、设备手册、工艺规范、质量标准和历史案例分散，版本和适用范围不清。普通 RAG 只做文档相似度
检索，不能自动结合实时生产数据，也容易引用已作废或不适用的资料。

### 3.5 分析依赖少数专家，结果难复用

SPC、分布、Pareto、OEE、工艺对比和异常诊断常依赖个人经验、Excel 模板或一次性脚本。计算方法、
筛选条件和排除规则没有形成稳定服务，结果难以复算和审计。

### 3.6 通用大模型缺少工业安全边界

企业不能允许模型任意执行 SQL、访问服务器文件、调用高风险业务接口或自行决定权限。网络中断、
MCP 失败、模型超时和任务取消也不能让业务状态失去控制。

### 3.7 每家客户不同，纯项目制难以复制

客户系统、字段、工艺和知识均不同。如果每次都修改 Agent 内核，项目会快速分叉，升级和维护成本
持续上升；如果强制客户使用统一后端，又很难进入已有 IT 体系。

## 4. 产品解决方案

```text
Web / 企业业务系统 / 移动端 / IM
                 |
       assistant_agent_api
                 |
       Industrial Agent Core
        /        |         \
   Skills   Capability     Governed Runtime
             Orchestrator
       /          |             \
Knowledge MCP  Business MCP  Analysis Provider
       |          |             |
RAG/文档平台  MES/WMS/QMS   分布/SPC/OEE/异常
设备手册/SOP  设备/时序库    确定性计算服务
```

Agent Core 只负责任务理解、能力选择、受控执行和结果解释。业务数据、知识存储和大规模计算留在靠近
数据源的位置，平台通过版本化契约获得有界结果。

核心处理原则：

> Compute near data, reason over governed results.

即“计算靠近数据，模型只推理受治理的结果”。

### 4.1 一次可信问答的标准链路

用户提问：

> 今天工艺电池片产量是多少？展示效率分布，并说明主要异常。

标准执行过程：

1. Agent 识别指标、时间和分析意图；
2. 指标语义层确认“今日”、产量口径、工厂/车间/产线和效率单位；
3. MES MCP 在数据源侧查询、过滤和聚合生产事实；
4. Analysis Provider 对全量有效样本执行确定性分布计算；
5. Agent 检查样本量、缺失值、数据延迟和异常警告；
6. Presentation 能力生成受控 ChartSpec，而不是任意前端代码；
7. Agent 返回结论、图表、查询范围、数据截至时间、来源和质量说明；
8. 用户可继续追问设备、批次、班次或工艺参数，Agent 在同一会话中下钻。

目标输出不是一句孤立数字，而是一份可判断、可追问、可复核的结果：

```text
截至 14:35，A 车间今日累计下线 128,420 片，其中合格 126,870 片。
效率有效样本 125,906 条，中位数 26.34%，主要集中于 26.2%～26.5%。

范围：A车间 / 1-4线 / 当前生产日
数据截至：2026-07-24 14:35 +08:00
来源：MES production-summary、cell-efficiency-distribution
数据质量：964 条效率缺失；图表展示 30 个服务端聚合区间
```

## 5. 产品模块与责任边界

### 5.1 平台必须掌控的能力

以下能力决定系统正确性和安全性，由我们开发并维护，不允许客户扩展侵入：

- Agent Loop 与任务执行状态机；
- Session、Run、暂停、取消、恢复和 checkpoint；
- 上下文、预算、失败分类和 Interaction；
- 工具注册、权限、调用路由和副作用恢复；
- Runtime Profile、Workspace、进程和资源隔离；
- Artifact、Dataset、Chart 和 Attachment 生命周期；
- 公共事件、错误码、服务 DTO 和版本策略；
- 日志、审计、脱敏和能力健康状态；
- 模型 Provider 适配与能力预检；
- 扩展清单、兼容校验和契约测试套件。

客户不通过修改 Agent Loop、RunState 或内部存储实现业务功能。

### 5.2 双方均可开发的扩展能力

| 模块 | 我们提供 | 客户/合作伙伴提供 |
|---|---|---|
| Skill | 格式、加载、信任、模板、工业通用 Skill | 企业术语、流程、诊断方法、工具使用规则 |
| Business MCP | 接入 SDK、权限、健康、通用接口模板 | MES/WMS/QMS/ERP/设备等真实连接器 |
| Knowledge | Knowledge 契约、RAG 参考实现、引用协议 | 文档、权限、版本规则或已有知识库服务 |
| Analysis | 通用确定性引擎和结果契约 | 专有算法、工艺模型、已有 Python/R 服务 |
| Metric Catalog | 通用指标模型、校验和版本机制 | 企业指标定义、组织维度、班次和生产日规则 |
| Industry Pack | 通用工业基础包和行业模板 | 客户专属配置、设备模型、业务流程 |

### 5.3 禁止扩展绕过的边界

- Skill 不保存密钥，不替代实时数据源；
- MCP 不决定最终用户权限，不返回无界明细；
- Analysis Provider 不向 Agent 注入任意执行代码；
- Knowledge Provider 不返回无来源、无版本的“事实”；
- 模型不直接执行任意 SQL，不自行计算 SPC；
- 外部模块不暴露服务器路径、内部凭据和未脱敏参数；
- 外部模块不能自定义破坏公共状态机的事件和终态。

## 6. 四类核心扩展

### 6.1 Professional Skills：专业工作方法

Skill 描述“遇到某类问题应该如何分析”，适合承载：

- 工业术语和业务上下文；
- 标准分析步骤和澄清问题；
- 指标选择与分层顺序；
- 何时调用知识、数据和分析工具；
- 结果解释规则和禁止性结论；
- 企业操作流程和升级路径。

Skill 不承载动态生产事实。通用 SPC Skill 可由我们维护，甲方 PECVD 异常诊断 Skill 可由客户或
实施团队维护。

### 6.2 Knowledge/RAG：文档知识与证据

知识库保存企业知识资产，RAG 是从知识库检索证据并交给模型回答的方法。工业知识服务至少需要：

- 全文和向量混合检索；
- 文档版本、生效和作废状态；
- 工厂、产品、产线、设备型号和工艺适用范围；
- 权限过滤；
- 章节级引用和原文定位；
- 重排和无可靠证据拒答；
- 文档更新后的索引一致性。

RAG 适合 SOP、设备手册、工艺规范和历史案例；实时产量、效率和 Cpk 必须走业务查询与确定性分析。

### 6.3 Business MCP：实时事实与业务动作

MCP 用于连接 MES、WMS、QMS、ERP、设备系统、Historian 和客户自有服务。推荐提供领域化工具，而
不是向模型暴露通用 SQL：

```text
get_production_summary
get_efficiency_distribution
compare_lines
get_quality_pareto
trace_material_batch
get_equipment_alarm_summary
```

平台统一管理工具能力、只读/写入副作用、权限、超时、熔断、审计和恢复。客户负责业务接口、字段映射、
凭据和内网部署。

### 6.4 Analysis Provider：确定性工业分析

大模型不直接承担统计计算。Analysis Provider 在数据附近完成：

- 描述统计、分位数和分布；
- 分组对比、趋势和移动窗口；
- Pareto、良率和缺陷分层；
- SPC、控制图、Cp/Cpk、Pp/Ppk；
- OEE、停机损失和设备对标；
- 统计检验、回归和工艺变更前后对比；
- 异常检测、变点和候选根因证据排序；
- 数据质量分析和可视化数据派生。

客户可接入专有算法，但必须返回统一 Analysis Result、方法版本、输入范围、质量警告和可复核 Artifact。

## 7. 大数据处理架构

工业 Agent 不能通过扩大模型上下文解决数据规模问题。数据按四级处理：

| 数据规模 | 处理方式 | Agent 可见内容 |
|---|---|---|
| 小型结果 | 直接结构化返回 | 指标、少量分组、Top N、统计摘要 |
| 中型结果 | Dataset Artifact | schema、行列数、摘要、有界预览、opaque ref |
| 大型分析 | Analysis Job | 进度、取消、最终摘要和结果 Artifact |
| 超大历史 | 查询/时序/湖仓引擎 | 仅接收服务端聚合、抽样或分析结果 |

数据源侧负责过滤、聚合、预计算、抽样、降采样和统计。模型不得接收百万行 JSON。

可选数据技术由客户现状决定，而不是由 Agent 强制指定：

- PostgreSQL：业务数据和中等规模分析；
- ClickHouse：大规模明细、聚合和时序分析；
- TimescaleDB/InfluxDB：设备时序；
- DuckDB/Polars：单机文件和边缘分析；
- Trino/Spark/Lakehouse：跨源和超大规模离线分析；
- Parquet：列式交换和归档。

每个分析结果至少携带：

```text
source / as_of / query_scope
population_count / valid_count / missing_count / excluded_count
sampled / sample_method
calculation_method / metric_version
data_quality_warnings / result_artifacts
```

图表渲染点数可以小于实际分析样本数，但必须同时展示 analyzed_count 和 rendered_points，避免误导。

## 8. 工业语义与公共契约

平台能否跨客户复制，关键不在于接入多少接口，而在于能否把不同客户的数据映射到稳定语义。

建议逐步形成以下版本化公共契约：

```text
CapabilityManifest       扩展身份、版本、权限和兼容范围
MetricDefinition         指标公式、单位、维度、时间语义和版本
IndustrialQueryRequest   受控筛选、分组、时间和指标请求
MetricResult             单值或小型聚合结果
DatasetArtifactRef       大数据集的 opaque 引用
DatasetSummary           schema、规模、统计和质量摘要
AnalysisRequest          分析类型、参数、输入和限制
AnalysisJob              大型任务状态、进度、取消和恢复
AnalysisResult           方法、结论、派生数据和 Artifact
DataQualityReport        缺失、排除、延迟、异常和采样事实
SourceEvidence           数据来源或知识文档的可追溯引用
```

同一种工具在不同客户环境可以由不同系统实现，但返回相同业务契约。例如平台定义
`ProductionSummaryResult`，客户实现自己的 `get_production_summary`。

## 9. 优先工业分析场景

产品按照“描述、监控、诊断、预测、优化”逐步演进。

### 9.1 第一层：描述发生了什么

- 产量、投入、产出、WIP、计划达成；
- 良率、一次通过率、效率分布；
- 班次、产线、机台、产品和批次对比；
- 缺陷 Pareto、停机 Pareto；
- 箱、盒、批次和物料谱系追溯。

### 9.2 第二层：监控是否稳定

- SPC 控制图和判异规则；
- Cp/Cpk、Pp/Ppk；
- 参数漂移、分布漂移和变点；
- OEE、MTBF、MTTR 和设备一致性；
- 单位产品电耗、水耗、气耗和材料消耗。

### 9.3 第三层：诊断候选原因

- 按 5M1E 分层；
- 工艺参数、设备、批次、Recipe 和班组关联；
- 异常前后窗口对比；
- 实时数据与设备手册、SOP、历史案例联合分析；
- 根因候选排序及支持/反对证据。

Agent 只能输出“证据支持的候选原因”，不能把相关性描述为确定因果。

### 9.4 后续：预测与优化

- 质量预测、故障预测和剩余寿命；
- 交付、缺料和产能风险预测；
- 参数窗口和工艺优化建议；
- 排产和能源优化。

预测和优化必须在数据质量、回测、漂移监控、人工审批和责任边界成熟后进入产品，首期不承诺自主调参。

## 10. 我们的方案优势

### 10.1 不绑定模型，也不绑定客户数据平台

云端和本地模型共用同一 Agent 能力边界；客户可以保留现有 MES、知识库、算法和数据基础设施，通过
标准扩展接入，降低替换成本和供应商锁定。

### 10.2 知识、实时事实和统计计算严格分工

- Skill 决定“怎么做”；
- Knowledge/RAG 提供“文档依据”；
- MCP 提供“实时业务事实和动作”；
- Analysis Provider 提供“确定性计算”；
- Agent 负责“何时调用、如何组合和如何解释”。

这种分工降低模型幻觉，并使每类能力可以独立测试和替换。

### 10.3 大数据不进入模型上下文

分析靠近数据执行，Agent 只接收指标、摘要、质量事实和受管 Artifact。方案能够覆盖从几十条汇总到
亿级工业历史数据，而不依赖无限上下文。

### 10.4 结果可追溯而不是只给答案

答案携带指标口径、查询范围、数据截至时间、样本量、缺失值、计算方法、来源和文档引用。对工业客户，
“为什么可以相信”与“答案是什么”同等重要。

### 10.5 扩展开放，核心治理不开放

客户能够开发 Skill、MCP、Knowledge 和 Analysis 扩展，但权限、审计、状态机、版本和数据边界由平台
控制。既满足定制需求，又避免项目分叉和安全失控。

### 10.6 已有可信执行基础

当前 Agent 已具备模型切换、工具权限、预算、暂停/取消/恢复、checkpoint、结构化失败、Runtime Profile、
MCP/Skill 接入、Attachment 和受控 Chart Artifact。这些能力可直接作为工业平台底座，而不必从普通
聊天应用重新开始。

## 11. 差异化与非目标

### 11.1 我们不做什么

- 不把产品定位为通用 BI 的完全替代品；
- 不让模型直接扫描工业数据库或自由生成生产 SQL；
- 不通过普通 RAG 回答实时指标；
- 不让模型自行完成无法复算的 SPC 和质量结论；
- 不承诺首期自动根因、质量预测或无人审批调参；
- 不把每个客户连接器写入 Agent Core；
- 不强制客户迁移知识库和数据平台。

### 11.2 与常见方案的区别

| 常见方案 | 主要限制 | 我们的方向 |
|---|---|---|
| 通用聊天机器人 | 会答但缺实时数据、统计和执行边界 | 受控编排知识、业务事实与分析 |
| 文档 RAG | 擅长文档，不擅长实时指标和大数据计算 | Knowledge 只是三类能力之一 |
| 固定 BI 报表 | 可信但只能回答预定义问题 | 自然语言驱动受控查询和下钻 |
| Text-to-SQL | 灵活但口径、权限和查询成本风险高 | 指标语义层 + 领域工具 + 查询策略 |
| 单体行业应用 | 能力完整但难适应客户已有系统 | 开放 Provider 与行业契约 |
| 纯项目定制 | 初期快，后续分叉和升级成本高 | 平台核心 + 行业包 + 客户扩展 |

## 12. 产品形态

建议形成四层可组合产品：

1. **Industrial Agent Platform**  
   Agent Core、API/Web、Runtime、治理、扩展 SDK 和契约测试。

2. **Industrial Foundation Pack**  
   Metric/Dataset/Analysis/Evidence 契约，分布、Pareto、SPC、OEE、趋势和基础 Skills。

3. **Industry Solution Packs**  
   光伏电池片、锂电、半导体、电子制造等行业指标、分析模板、图表和 MCP 参考实现。

4. **Customer Extensions**  
   客户 MES/WMS/QMS 连接器、企业知识库、专属 Skill、指标定义和专有算法。

商业交付不应只按“开发一个聊天机器人”计价，而可以组合平台授权、行业包、连接器实施、知识治理、
专有分析和持续运维。

## 13. 路线图

### 阶段 A：工业问答最小闭环

目标：可靠回答生产事实，并展示受控图表。

- 冻结 Metric、Dataset、DataQuality、Evidence 基础契约；
- 建立扩展 Capability Manifest；
- 完成一个电池片 MES MCP 垂直样板；
- 支持今日产量、良率、效率分布和按产线/班次下钻；
- 形成 Dataset Artifact 与大结果边界；
- Web 展示查询范围、来源、截至时间和质量警告。

验收问题：

> 今天各产线生产多少电池片？效率分布有什么差异？数据截至几点？

### 阶段 B：工业分析基础包

目标：形成可复用、可复算的确定性分析能力。

- 分布、趋势、分组对比和 Pareto；
- SPC、控制图和过程能力；
- OEE、停机和设备对标；
- Analysis Request/Result 和算法版本；
- Analysis Job 进度、取消、恢复和 Artifact；
- 分析 Eval 与基准数据集。

### 阶段 C：企业知识与联合诊断

目标：把实时事实与文档知识结合。

- Knowledge Provider/MCP 契约；
- 混合检索、重排、版本和适用范围；
- 引用、证据和无依据拒答；
- 工业通用 Skill 与客户 Skill SDK；
- 数据异常与 SOP、设备手册、历史案例联合回答。

### 阶段 D：平台化与客户扩展生态

目标：降低每个客户的实施和升级成本。

- 扩展 SDK、模板、契约测试和兼容矩阵；
- 模块安装、签名、健康、熔断和版本治理；
- 租户、项目、数据权限和资源配额；
- 客户部署包、观测、审计和运维工具；
- 第一套光伏行业解决方案包。

### 阶段 E：高级诊断、预测与优化

进入条件：数据质量可度量、算法可回测、用户反馈闭环和人工审批机制成熟。

- 多变量异常和候选根因；
- 质量预测、设备健康和交付风险；
- 工艺窗口与排产优化建议；
- 模型/算法漂移监控；
- 高风险建议的人机审批和效果追踪。

## 14. 成功指标

产品不能只用“回答率”衡量。建议建立以下指标：

### 用户价值

- 从提问到可信答案的中位时间；
- 替代人工取数、拼表和初步分析的工时；
- 高频问题自助完成率；
- 问题下钻次数和结果复用率；
- 工程师对答案证据和口径的认可率。

### 正确性与可信度

- 指标口径匹配率；
- 带来源、范围和 `as_of` 的回答比例；
- 数据质量警告召回率；
- 无依据时正确拒答率；
- 确定性分析复算一致率；
- 错误工具调用和越权调用拦截率。

### 平台与生态

- 新客户首个 MCP/Knowledge Provider 的接入周期；
- 不修改 Agent Core 完成的需求比例；
- 扩展契约测试通过率；
- MCP/分析服务故障降级成功率；
- 单次问题的模型 token、数据扫描量和端到端延迟；
- 版本升级后客户扩展兼容率。

## 15. 风险与控制

| 风险 | 后果 | 控制原则 |
|---|---|---|
| 指标语义错误 | 数字正确但业务结论错误 | 指标目录、版本、时间和维度显式化 |
| 模型幻觉 | 编造来源、原因或操作 | 工具事实优先、引用、无依据拒答 |
| 大数据直传 | 超窗、延迟、泄漏、计算错误 | 数据源侧计算 + Dataset/Job Artifact |
| 相关性被描述成因果 | 错误工艺决策 | 候选原因 + 支持/反对证据 + 人工确认 |
| 客户扩展失控 | 越权、分叉、不可升级 | Capability、沙箱、审计、契约测试 |
| MCP/数据源故障 | 长任务卡住或重复失败 | optional 启动、timeout、熔断、降级和恢复 |
| 知识版本错误 | 引用作废 SOP | 生效/作废、适用范围、权限和原文定位 |
| 算法口径不一致 | SPC 等结果无法复算 | 确定性算法、方法版本和基准测试 |
| 预测误用 | 生产或质量损失 | 回测、置信度、漂移监控、人工审批 |

## 16. 当前基础与下一步

### 16.1 已有基础

当前仓库已经具备工业 Agent 平台所需的部分底座：

- UI 无关的 Agent Service；
- 模型 Provider 切换和能力预检；
- Skill 与 MCP 接入；
- Runtime Policy、权限、预算和审计；
- Run 暂停、取消、恢复和结构化失败；
- Session、Attachment、Artifact 与受控 ChartSpecV2；
- API/Web 可消费的稳定事件边界。

### 16.2 尚未实现

以下为目标能力，不应在售前或文档中表述为已交付：

- 工业 Metric/Dataset/Analysis/Evidence 正式契约；
- 通用工业 Analysis Provider；
- SPC/OEE/Pareto 等工业分析基础包；
- Knowledge Provider 和工业 RAG；
- 电池片 MES 垂直样板闭环；
- Analysis Job 和大数据 Dataset Artifact；
- 客户扩展 SDK、签名、熔断和兼容测试平台；
- 多租户、企业权限和生产部署治理。

### 16.3 建议立即启动的产品工作

在修改 Agent Loop 之前，先完成阶段 A 的产品发现与契约设计：

1. 选择一家真实或模拟电池片工厂作为样板；
2. 访谈生产、工艺、质量、设备、IT 五类角色；
3. 收集 30～50 个真实问题并按频率、价值、风险分级；
4. 冻结“今日产量、良率、效率分布”三个指标口径；
5. 记录数据源、时区、班次、延迟、缺失和权限事实；
6. 设计 MetricResult、DatasetSummary、DataQualityReport 和 Evidence；
7. 用一个外置 MES MCP 和一个确定性分布工具跑通端到端；
8. 用真实问题建立工业问答 Eval，而不是只测试工具是否调用成功。

## 17. 待验证假设

本蓝图中的以下判断需要通过客户访谈和试点验证：

- 第一批客户是否更愿意从生产运营问答还是质量/SPC 切入；
- 客户是否已有可复用 RAG、指标平台和算法服务；
- 哪些数据必须完全本地处理，哪些摘要可以进入云模型；
- 工艺和质量工程师可接受的响应时间；
- 客户是否允许 Analysis Job 在后台运行并稍后通知；
- 甲方最愿意付费的是平台授权、行业分析包还是连接器实施；
- 用户是否信任自然语言查询，还是要求先展示筛选范围再执行；
- 数据来源、算法版本和质量说明需要展示到什么粒度。

这些假设未验证前，不应过早开发多 Agent、自主调参、复杂预测或大规模插件市场。

## 18. 产品调研计划

正式对外定版前，建议单独完成一轮产品调研：

1. **客户问题调研**：角色访谈、任务观察、报表/Excel/工单采样；
2. **数据可行性调研**：系统清单、接口、延迟、数据量、权限和质量；
3. **竞品调研**：工业 Copilot、制造数据平台、知识问答、BI Copilot 和工业分析软件；
4. **替代方案调研**：人工、固定报表、自助 BI、Text-to-SQL、RAG 和项目制机器人；
5. **概念验证**：用同一组真实问题比较耗时、正确率、可追溯性和实施成本；
6. **商业验证**：部署模式、采购主体、试点周期、验收指标和付费意愿。

竞品调研重点不应是“谁的聊天界面更好”，而应比较：

- 能否连接实时工业数据；
- 是否有指标语义和大数据边界；
- 是否提供确定性工业分析；
- 是否保留来源、时间、样本和算法证据；
- 是否支持私有部署与客户扩展；
- 扩展是否侵入核心；
- 故障、权限、审计和恢复是否完整；
- 从试点到复制的实施成本。

---

本蓝图的核心产品判断是：

> 工业 Agent 的壁垒不是让模型知道更多术语，而是建立一套可连接客户系统、可处理大规模数据、
> 可复算分析结果、可追溯证据并允许客户安全扩展的编排与治理平台。
